# Agent 提交门禁 + 评审模板

> **本技能是一份给「智能体（Agent）」使用的提交门禁 SOP 与模板集。**
> 它把「AI 代人类提交代码」这一高风险动作升级为一道硬门禁：Agent 不是写完代码就直接 commit，
> 而是充当**提交守门员**——先把范围圈死、把风险评出来、把分数算出来、把模板填实、把缺项问清、
> 把记录落到仓库里，最后才允许提交。未完成门禁全流程前，**禁止执行任何 git commit / git push / 提 MR 动作**。

## 一、门禁定位与角色

| 项 | 约定 |
| --- | --- |
| 门禁角色 | Agent = 提交守门员（评审 + 打分 + 模板填充 + 追问 + 落记录），不抢占最终提交权 |
| 触发即门禁 | 用户表达「提交/commit/提 MR/合并请求/push」，或 Agent 即将执行 `git commit`/`git push`/`gh pr create` 之前 |
| 门禁硬规则 | 未依次走完对应门禁流程（完整通道七步 / 轻量化通道四步）前，禁止提交 |
| 通道分流 | **改动小（diff < 150 行）且无重点影响（不命中任何高风险项）-> 默认走轻量化通道（四步）**；否则走完整通道（七步）；命中高风险或快检不达标自动升级回完整通道 |
| 演练模式 | 用户要求「演练/试运行/检验」本技能时：按判定通道完整走完（完整通道七步 / 轻量化通道四步）并输出，仅在「落提交记录」前询问是否真实生成文件 |
| 模板原则 | 所有模板**章节与顺序固定**，Agent 只能填空、不得增删章节或重排 |

## 二、门禁流程（七步 · 模板化执行）

> 每一步给出「Agent 动作 + 产出模板/产物」。任一步不达标即按对应挡位处置，不得静默放行。

**Step 1 · 收集事实（禁止凭空编写）**
- `git status` + `git diff --staged`（或 `git diff`）读取真实改动
- `git log --oneline -5` 取近期提交风格；`git config user.name` 取提交者
- 产出：真实改动清单（不得臆测）

**Step 2 · 圈定提交范围（先定范围再评审）**
- 评审对象 = **本次待提交内容**，不是全部工作区改动
- 已 staged -> 评 `git diff --staged`；未 staged -> 仅评用户指定文件 `git diff -- <paths>`
- 提 MR/评审已有提交 -> 评 commit 区间 diff（如 `git diff <base>...HEAD`），不含工作区未提交改动
- 列出改动文件清单请用户确认纳入项，**不得默认全量纳入**
- 范围一经确认：后续评审、MR 描述、规模统计、提交记录「变更规模」**均以该范围为口径**

**Step 3 · 判定门禁通道（分流）**
- **改动小且无重点影响**（圈定范围 diff **< 150 行** 且 **不命中任何高风险项**）-> **默认走【轻量化门禁通道】**（第五节 · Agent 一等提交路径，四步即可完成门禁）
- 否则（>= 150 行 或 命中高风险）-> 走【完整门禁通道】（Step 4~7）
- 轻量化通道内一旦命中高风险或快检不达标 -> **自动升级回完整通道**（见第五节）

**Step 4 · 门禁评审 + 打分（完整通道）**
- 按【评审 Checklist 与评分模板】逐项核查，每项记录判定 + 证据（文件:行号），禁止无证据判定
- 产出风险清单（blocking / suggestion / nit）与可复算总分
- 按【高风险项清单】识别并单列高风险项

**Step 5 · 填写 MR 描述模板**（内容必须来自圈定范围真实 diff）
- 按【MR 描述模板（完整）】逐节填写；关联需求/缺陷号未知先追问
- AI 参与改动勾选 `[AI-assisted]`/`[AI-generated]`，工具填真实工具名，提示词摘要写本次任务要点
- 自检清单逐项真实核查后勾选：统计圈定范围 diff 行数验证 <= 400 行（提交记录文件不计入）；若超限主要来自 lock 文件、自动生成代码、纯格式化或批量重命名，剔除这些非业务改动后实际业务改动仍 <= 400 行，则视为满足规模要求，并在提交记录「说明」栏注明剔除口径；搜索 password/secret/token/key 排查硬编码密钥；接口/公共方法变更用 Grep 列全调用方；无法核实项保持未勾选并说明

**Step 6 · 追问补全 + 输出确认**
- 按【集中追问模板】盘点必填项，缺失项**一次性集中追问**，得到答复再填写
- 输出「MR 描述 + 评审结果（风险/评分/高风险项）」，等待用户确认或修正

**Step 7 · 落提交记录 + 按确认方式提交**
- 按【提交记录文件模板】把 MR 描述 + 评审结果写入仓库根 `提交记录/` 目录，随版本提交
- 按【提交方式与 IDEA 协同模板】执行提交（文件清单已在 Step 2 确认，此处仅确认提交方式）
- 用户要求修改 MR/评审结论时，先按修改后版本更新提交记录文件再提交

## 三、评审 Checklist 与评分模板

> **评审对象 = Step 2 圈定的本次待提交 diff**。核查证据允许全局 Grep，但**判定只针对本次 diff 引入的变更**；
> 范围外发现（顺带看到的其他文件缺陷）不进评分、不阻断本次提交，以「范围外观察」附注提示用户。

### 3.1 通用 Checklist（权重 60%）

| #  | 核查项 | 核查方法 |
| -- | ---- | ---- |
| G1 | 逻辑正确，边界条件（空值/0/极值/超长）已处理 | 阅读 diff 逻辑分支 |
| G2 | 异常处理不吞异常，日志不含敏感信息 | 检查 catch/日志语句 |
| G3 | 无并发问题，事务边界正确 | 检查共享状态/事务注解 |
| G4 | 无重复实现（是否已有公共工具方法） | Grep 相似实现 |
| G5 | 命名清晰，无魔法数字 | 阅读 diff |
| G6 | 无 N+1 查询、无慢 SQL、无内存泄漏风险 | 检查循环内查询/资源释放 |
| G7 | 测试覆盖关键分支，断言验证的是需求而非实现 | 查看测试 diff 与断言 |

### 3.2 AI 代码专项 Checklist（权重 40%；未标注 AI 参与时并入通用项，通用项权重升为 100%）

| #  | 核查项 | 核查方法 |
| -- | ---- | ---- |
| A1 | 调用的 API/方法真实存在（防幻觉 API） | Grep 定义处确认存在 |
| A2 | 无顺带重构与无关改动（diff 最小化） | 逐文件核对 diff 与任务目标 |
| A3 | 业务约束、历史兼容、边界规则未被破坏 | 对照调用方与既有逻辑 |
| A4 | 未引入重复的已有实现 | Grep 相似实现 |
| A5 | 安全/鉴权/加密/支付逻辑已由专人复核 | 标注待复核对象 |
| A6 | 提交人能解释每一处关键逻辑 | 列出 3 处供人复核的追问点 |
| A7 | 影响面自查清单与实际改动一致 | 核对调用方搜索结果 |

> 纯文档/配置类变更中不适用代码项标 N/A 剔除，**N/A 项不参与分母，避免拉低分数**。

### 3.3 评分模板（客观、可复核）

- 每项判定：通过=1 ｜ 有风险=0.5 ｜ 不通过=0 ｜ N/A 剔除
- 维度得分 =（通过数 + 0.5x有风险数）/ 适用项数 x 100；**某维度适用项数为 0 时该维度记 N/A，权重按剩余维度重新分配**
- 总分 = 通用项得分 x 60% + AI 专项得分 x 40%（未标注 AI 时 = 通用项得分 x 100%），四舍五入取整
- 权重弹性：通用/AI 固定按 60%/40% 计；当 AI 参与改动占比明显偏离（如明显偏低或偏高）时，可在 40%±10% 区间内按实际占比微调通用/AI 权重，并在评分明细中说明调整理由，避免对纯手写或纯生成代码失真
- 必须输出评分明细表（每项判定 + 证据），总分可复算，禁止凭印象打分

### 3.4 风险分级与挡位处置模板

| 级别 | 含义 | 处置 |
| ---- | ---- | ---- |
| blocking | 必须改（逻辑错误、安全问题、影响面未确认） | 默认阻断；用户坚持需在提交记录标注「明知风险强制提交」 |
| suggestion | 建议改 | 随 MR 描述公示，不阻断 |
| nit | 可选优化 | 记录即可 |

| 总分挡位 | 门禁结论 |
| ---- | ---- |
| >= 90（绿） | 放行提交 |
| 75-89（黄） | 放行，风险随 MR 公示 |
| 60-74（橙） | 建议修复后提交；用户确认继续才提交，提交记录标注 |
| < 60（红）或存在 blocking 不通过 | 高风险，默认阻断，需修复或 Tech Lead 明确批准 |

### 3.5 高风险项清单（满足任一即列出，高风险须提示「需 Tech Lead 审批后方可合入」）

1. 改动属于高风险范围：公共库/基础组件、对外接口、数据库结构、权限与鉴权、资金与计费、AI 生成的核心逻辑
2. 存在任一 blocking 级问题
3. 公共方法/接口/数据结构变更但调用方清单不完整或未确认
4. 测试缺失、断言被改以适配实现、或覆盖率低于主干基线
5. 总分落入红挡（< 60）

## 五、轻量化门禁通道（Agent 轻量提交路径 · 改动小且无重点影响）

> **轻量化通道是本技能的一等提交路径，不是完整通道的降级备注。** 只要满足下面「改动小 + 无重点影响」两条，
> Agent **默认即走本通道**，用最小流程完成门禁；一旦命中高风险或快检不达标，自动升级回完整通道（Step 4~7）。

**适用前提（两条核心 + 一条兜底，任一不满足立即回退完整通道）**：
- **改动小**：圈定范围 diff **< 150 行**（新增+删除合并计，提交记录/模板文件不计入统计）；若行数主要来自 lock/生成物/格式化，剔除后实际业务改动仍 < 150 行则视为满足，并在提交记录说明剔除口径
- **无重点影响**：**不命中**高风险项清单任一条件（非公共库/基础组件、非对外接口、非数据库结构、非权限鉴权、非资金计费、非 AI 生成核心逻辑）
- 改动文件本身无历史 blocking 级遗留

**轻量门禁流程（四步 · 完整通道七步的压缩版）**：
- **轻量 Step L1 · 收集事实 + 圈定范围**：同 Step 1~2，用 `git status` / `git diff` 取真实改动并确认纳入文件；据此判定是否满足上面前提，任一不满足立即切完整通道。
- **轻量 Step L2 · 轻量快检 + 打分**：按下表 Q1~Q4 逐项核查并给证据（文件:行号），计算可复算总分；出现任一不通过 或 总分 < 75 -> **自动升级回完整通道**。
- **轻量 Step L3 · 填轻量 MR 模板 + 集中追问**：按【轻量 MR 描述模板（仅 4 节）】填写；关联需求号、验证方式等缺失项按【集中追问模板】一次性集中追问。
- **轻量 Step L4 · 落记录 + 按确认方式提交**：生成简化提交记录（顶部标注「轻量化通道」），按【提交方式与 IDEA 协同模板】执行提交，兜底校验照常执行。

（下面 Q1~Q4 快检、轻量打分、轻量 MR 模板即为流程步 Step L2~L3 的具体模板；快检用 Q 前缀，与流程步 L 前缀区分，避免编号撞名）

**轻量快检（4 项，逐项给证据，禁止走过场）**：

| #  | 快检项 | 方法 |
| -- | ---- | ---- |
| Q1 | 逻辑与边界正确（空值/0/极值/超长已处理） | 阅读 diff 分支 |
| Q2 | 调用的 API/方法真实存在（防幻觉） | Grep 定义处确认 |
| Q3 | 无顺带重构/格式化/批量重命名，无硬编码密钥 | 逐文件核对 diff 与任务目标 + 搜索敏感词 |
| Q4 | 公共方法/接口变更已列出调用方（仅涉及接口变更时） | Grep 调用方 |

**轻量打分**：每项 通过=1 / 有风险=0.5 / 不通过=0 / N/A 剔除，总分 = 得分 / 适用项数 x 100，四舍五入取整，挡位沿用完整通道（绿 >=90 / 黄 75-89 / 橙 60-74 / 红 <60）。出现任一不通过 或 总分 < 75 -> **自动升级回完整通道**。

**轻量 MR 描述模板（仅 4 节）**：

```markdown
## 变更背景与内容
（关联 #XXXX；一句话说明改了哪个模块、核心改动）

## AI 使用情况
- [ ] 未使用 AI
- [ ] [AI-assisted] 工具：___（AI 参与比例高时升级完整通道）

## 轻量快检
- [ ] Q1 逻辑与边界正确
- [ ] Q2 API 真实存在（Grep 确认）
- [ ] Q3 无顺带改动 / 硬编码密钥
- [ ] Q4（如涉及接口）调用方已列出

## 验证与回滚
（一句话：本地如何验证 + 出问题如何回滚）
```

> 设计原则：轻量化通道**降的是流程重量，不降风险底线**。**改动小且无重点影响 -> Agent 默认走本通道**；任何高风险命中或快检不达标 -> 一律回到完整通道。
> 提交记录文件仍生成（内容用简化版：快检表 + 总分 + 变更规模 + 顶部标注「轻量化通道」）；提交方式沿用第七节，兜底校验照常执行。

## 六、提交记录文件模板

> MR 描述确认后、git commit 之前生成。

- **目录**：仓库根 `提交记录/`，不存在则创建
- **命名**：`{类型}_{提交者}_{YYYYMMDD}_{序号}.md`
  - 类型：`需求`（有关联需求号）/ `缺陷`（缺陷修复）/ `其他`（文档、配置等无关联）——由追问结果确定，无法确定时追问
  - 提交者：`git config user.name`；日期：当天 YYYYMMDD
  - 序号：同提交者同日已有记录数 + 1，两位数字（先查目录，不存在从 01 起）

```markdown
# 提交记录：{一句话标题}

| 项 | 内容 |
| --- | --- |
| 提交者 | {git user.name} |
| 日期 | {YYYY-MM-DD} |
| 变更类型 | 需求 / 缺陷 / 其他 |
| 关联编号 | #XXXX 或 无 |
| 变更规模 | {N 个文件，+x -y 行} |
| 门禁通道 | 完整 ｜ 轻量 |
| 评审总分 | {XX}/100（{绿/黄/橙/红}） |
| 高风险项 | 无 ｜ 有：{简列} |
| 高风险处置 | 不涉及 ｜ Tech Lead 审批 ｜ 强制提交说明 |

## 一、MR 描述
（模板填写全文，与 MR 平台内容一致）

## 二、代码评审结果
### 2.1 Checklist 核查明细
| 项 | 判定 | 证据（文件:行号） |
### 2.2 风险清单
| 级别 | 位置 | 问题描述 | 建议 |
### 2.3 评分明细
| 维度 | 得分 | 权重 |
（总分与复算过程）
### 2.4 高风险项
（逐项列出或「无」）

（强制提交、豁免、待补充事项等，无则写「无」）
```

- 提交记录文件与业务变更**进入同一次 commit**，实现记录随版本留存；不计入单 MR <= 400 行统计

## 七、提交方式与 IDEA 协同模板

技能不抢占提交权，方式二选一（用户未声明时追问一次）：

### 方式一：AI 代提
- 逐文件 `git add <明确路径>`，**禁止 `git add -A` / `git add .`**，只提交清单内文件
- 未列入清单的本地改动（进行中工作、临时文件、个人配置）保持原状，不暂存、不提交
- commit message 按仓库近期风格给出，提交后回显结果

### 方式二：IDEA / 用户自提
技能**不执行 git commit**，改为输出「IDEA 提交指引」：
- **提交清单**：逐个列出应勾选文件路径（业务变更文件 + `提交记录/` 下本次记录文件）
- **changelist 建议**：上述文件放入同一 changelist（如 `commit-YYYYMMDD-序号`），避免提交记录文件漏勾
- **commit message**：给出可直接粘贴的主题行（及正文）
- 用户在 IDEA 提交面板按清单勾选；**提交记录文件务必与业务文件同次勾选**

### 兜底校验（两种方式都执行）
- **AI 代提**：commit 后用 `git status` + `git log -1 --stat` 校验业务文件与提交记录文件是否同次入库
- **IDEA 自提**：AI 无法感知 IDE 内提交时刻，校验在两个时点执行——用户回话「已提交」时；下次触发本技能时先回查 `git log -- 提交记录/` 确认上次记录文件是否入库
- 若提交记录文件被漏勾：提示用户并补一个独立 commit（`chore(commit-record): 随附 {原提交主题}`），并在提交记录「说明」栏补注实际所在 commit

## 八、集中追问模板

> 输出 MR 描述前盘点必填信息，有缺失时**必须先追问，不得用占位符糊弄**。

| 缺失信息 | 优先获取方式 | 仍缺失时追问话术 |
| ---- | ---- | ---- |
| 本次提交范围（哪些文件纳入） | git status 清单 + 用户勾选确认 | 「本次提交包含哪些文件？（列出清单供确认）」——**必须在评审前确定** |
| 变更类型（需求/缺陷/其他） | 由变更背景推导 | 「本次变更是需求、缺陷修复还是其他（文档/配置）？」 |
| 需求/缺陷号 | 需求单、用户输入 | 「本次改动关联哪个需求/缺陷号？」 |
| 影响范围（调用方） | Grep 代码搜索 | 搜索结果有歧义时列出候选清单让用户确认 |
| 验证方式 | 流水线记录、用户输入 | 「如何验证：步骤、环境、预期结果是什么？」 |
| 回滚方案 | 发布方式、用户输入 | 「出问题时如何恢复（回滚版本/回滚脚本）？」 |

追问规则：**一次性集中追问**全部缺失项，不得挤牙膏式逐条反复追问；用户明确「先提交后补/占位」才保留占位符并标注「待补充」；用户拒答或确实无法提供的项保留占位**禁止虚构**；AI 使用情况/自检清单/Checklist 判定与评分由 Agent 自行核实填写，不依赖用户提供。

## 九、门禁红线（不可逾越）

- 未走完「范围->评审->打分->模板->追问->记录->确认」七步前，**禁止执行任何 git commit / git push / 提 MR**
- MR 模板、提交记录模板章节与顺序固定，不得新增/删除/重排
- `git add` 只允许逐文件精确添加，禁止 `git add -A` / `git add .`；未列入清单的文件不得暂存
- 用户选择 IDEA 自提时，技能不得代为执行 git commit，只输出提交指引
- 所有勾选项必须有真实依据，未核实的不勾选并说明
- Checklist 判定与评分必须附证据（文件:行号），总分须可复算，禁止凭印象打分
- 评审不通过（红挡/blocking）不得静默放行：要么修复，要么用户/Tech Lead 明确批准并在提交记录中留痕
- 只有用户知道的信息（需求号、验证环境、回滚方式等）缺失时必须先追问，经用户确认跳过才可保留占位符并标注「待补充」
- 不为通过检查而虚报或修改事实（如测试断言）
- 提交记录文件命名与目录结构不得随意变更；当日重复提交按序号递增，不得覆盖旧记录
