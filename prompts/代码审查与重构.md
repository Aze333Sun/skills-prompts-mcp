# 代码审查与重构提示词

## 1. PR 代码审查

```
你是一位资深 {语言} 代码审查者。请审查以下 Pull Request 的变更：

```diff
{粘贴 git diff 或代码变更}
```

审查维度（按优先级排序）：
1. **正确性**：逻辑是否正确？边界条件是否处理？有没有 race condition？
2. **安全性**：是否有注入风险？敏感数据是否泄露？权限校验是否完整？
3. **性能**：是否有 N+1 查询？不必要的循环？大对象拷贝？
4. **可维护性**：命名是否表意？函数是否过长？职责是否单一？
5. **一致性**：是否遵循项目现有模式？错误处理风格是否统一？

输出格式：
- 🔴 严重（必须修改）：{问题 + 具体行号 + 修复建议 + 修复后代码}
- 🟡 建议（应该修改）：{问题 + 理由}
- 🟢 赞赏（做得好）：{具体哪里好}
```

## 2. 代码坏味道识别

```
请审查以下代码，识别所有代码坏味道（Code Smell）：

```{语言}
{粘贴代码}
```

对照 Martin Fowler《重构》中的坏味道分类：
1. 过长函数（> 30 行为信号）
2. 过大类（> 300 行或 > 10 个公共方法）
3. 重复代码（相同逻辑出现 2 次以上）
4. 过长参数列表（> 4 个参数）
5. 发散式变化（一个类因不同原因被修改）
6. 霰弹式修改（一个变化导致多处修改）
7. 依恋情结（函数过度使用其他类的数据）
8. 数据泥团（总是同时出现的多个字段）
9. 基本类型偏执（用 string 替代有意义的类型）
10. Switch 语句（多态可以替代的分支）

对每个坏味道：标注位置、严重程度、推荐重构手法、重构后代码。
```

## 3. 函数重构

```
请重构以下函数。要求：

源代码：
```{语言}
{粘贴函数代码}
```

重构目标：
1. 单一职责：每个函数只做一件事
2. 提取条件为命名函数（复杂 if 条件 → 语义化函数）
3. 消除嵌套（卫语句代替深层 if-else）
4. 减少参数（> 3 个参数 → 参数对象）
5. 命名优化（变量名准确表达意图，不用缩写）
6. 删除死代码和注释掉的无用代码
7. 确保重构后行为完全不变

输出：重构后代码 + 每个改动的理由（1 句话）。
```

## 4. 面向对象重构

```
请将以下面向过程的代码重构为面向对象设计：

```{语言}
{粘贴代码}
```

要求：
1. 识别并提取领域实体（Entity / Value Object）
2. 行为与数据封装在一起（Tell, Don't Ask）
3. 使用策略模式替代 if-else / switch 分支
4. 依赖注入替代硬编码依赖
5. 接口隔离（调用者不应依赖它不使用的方法）
6. 保持 SOLID 原则

输出：重构后类图（文字描述）+ 核心代码 + 设计取舍说明。
```

## 5. 性能优化重构

```
请分析并优化以下代码的性能瓶颈：

```{语言}
{粘贴代码}
```

排查清单：
1. 不必要的循环嵌套（O(n²) → O(n)）
2. 循环内的数据库查询（批量查询优化）
3. 重复计算（缓存/记忆化）
4. 不合理的同步阻塞（→ 异步/并行）
5. 大对象频繁创建（对象池/复用）
6. 多余的数据拷贝
7. 循环内的字符串拼接（→ StringBuilder/join）

输出：优化后代码 + 复杂度变化 + 预估性能提升。
```

## 6. 测试重构

```
请重构以下测试代码，提升其可维护性：

```{语言}
{粘贴测试代码}
```

要求：
1. 消除重复的 Setup（提取工厂函数 / beforeEach）
2. 参数化测试替代多个相似用例
3. 每个测试只测一个行为（一个 Assert 概念）
4. 测试命名遵循「被测方法_场景_预期行为」格式
5. 消除测试间的相互依赖（每个测试独立）
6. Mock 只用于外部边界（不用 Mock 替代简单值对象）

输出重构后完整测试代码。
```

## 7. SQL 查询重构

```
请优化以下 SQL 查询：

```sql
{粘贴 SQL 或 ORM 生成的查询}
```

要求：
1. 分析执行计划，找出最耗时的节点
2. 添加/调整索引建议
3. 消除不必要的 JOIN 和子查询
4. 用窗口函数替代子查询（如适用）
5. 分页查询优化（深分页问题）
6. 写出优化后的 SQL 和预期的性能提升

目标：从秒级降到 50ms 以内。
```

## 8. 状态管理重构

```
请重构以下 React/Vue 组件的状态管理：

```tsx
{粘贴组件代码}
```

要求：
1. 识别并消除冗余状态（derived state → 计算属性）
2. 状态提升/下沉（state 放在真正需要它的最小公共祖先）
3. 用 useReducer/状态机替代多个 useState
4. 提取自定义 Hook/Composable 封装状态逻辑
5. 消除 prop drilling（Context/Provide 是否真的需要？先考虑组件组合）
6. 异步状态统一用 loading/error/data 三元组管理

输出重构后代码 + 状态流转图（文字描述）。
```

## 9. 错误处理重构

```
请审查并重构以下代码的错误处理：

```{语言}
{粘贴代码}
```

分析维度：
1. 是否有吞掉异常的地方（空 catch 块）
2. 错误信息是否足够定位问题（包含上下文）
3. 自定义异常类型是否合理
4. 错误边界（全局异常处理中间件/ErrorBoundary）
5. 重试策略是否合理（指数退避、最大次数）
6. 降级与熔断逻辑
7. 用户友好的错误提示 vs 开发者日志

输出：重构后代码 + 错误处理策略说明。
```

## 10. 全面重构计划

```
我需要对一个 {项目规模} 的 {语言} 项目进行全面重构。请帮我制定一个安全的重构计划。

项目信息：
- 代码规模：{行数/文件数}
- 主要问题：{列举 3-5 个最头疼的问题}
- 测试覆盖率：{百分比}
- 业务重要性：{核心/非核心}

请输出：
1. 重构目标（优先解决什么问题，做什么，不做什么）
2. 重构顺序（从改动影响最小的模块开始）
3. 安全措施（每步如何确保行为不变：特征测试、快照测试、灰度）
4. 风险清单及缓解措施（Top 5 风险）
5. 阶段性里程碑（每个阶段的可验证成果）
6. 预计时间线

核心理念：小步快跑，每次提交都可上线。不做大爆炸式重构。
```
