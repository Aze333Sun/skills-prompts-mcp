# 调试与排错提示词

## 1. 错误日志分析

```
请帮我分析以下错误日志，定位根因。

应用环境：{语言/框架/版本}
发生时间：{时间}
错误上下文：{用户操作 / 触发条件}

```
{粘贴错误日志/堆栈跟踪}
```

请逐一分析：
1. 异常类型与含义（用简单的语言解释这个错误是什么）
2. 堆栈跟踪解读（从最内层逐帧分析，哪一行代码触发的）
3. 可能的原因（列出 2-3 个最可能的原因，按概率排序）
4. 验证方法（如何复现和确认每个可能原因）
5. 修复方案（对每个原因给出具体修复代码）
6. 预防措施（如何避免同类问题）

优先考虑最简单的原因（Occam's Razor），不要过早下结论。
```

## 2. 性能瓶颈定位

```
请帮我定位以下系统的性能瓶颈：

系统描述：{架构、技术栈、流量规模}
现象：{如：用户列表页加载 > 3 秒，P99 接口响应 > 2 秒}

提供的信息：
{性能监控数据 / APM 截图描述 / 慢查询日志 / profiler 输出}

请按以下步骤分析：
1. 确认瓶颈在哪一层（前端 → 网络 → 网关 → 应用 → 数据库 → 第三方）
2. 用数据量化（XX 操作占总耗时的 Y%）
3. 最可能的瓶颈根因
4. 短期修复（1 天内可上线，不改架构）
5. 长期优化（重构/改架构方案）
6. 需要添加的监控指标（让下次定位更快）
```

## 3. 内存泄漏排查

```
请帮我排查以下代码中的内存泄漏问题：

```{语言}
{粘贴代码或描述内存增长现象}
```

现象：{如：运行 24 小时后内存从 200MB 涨到 4GB}

分析步骤：
1. 哪些对象可能没有被 GC 回收
2. 闭包/回调是否持有大对象引用
3. 定时器/事件监听/订阅是否未清理
4. 缓存/集合是否无限增长
5. 第三方库是否有已知内存泄漏
6. 给出修复代码 + 内存泄漏验证方法（如何确认修好了）
```

## 4. 生产事故应急

```
我正在处理一个生产事故，需要快速帮助：

事故现象：{用户看到的错误/监控告警内容}
影响范围：{多少用户/哪些功能受影响}
最近变更：{最近上线了什么}

请帮我：
1. 立即止损方案（降级开关？回滚？限流？流量切换？）
2. 快速定位方案（查什么日志/监控，用什么命令）
3. 恢复验证清单（确认修复生效的检查项）
4. 事故时间线模板（方便后续复盘填写）

回答要简洁、可立即执行。优先级：止损 > 定位 > 修复。
```

## 5. 网络请求调试

```
请帮我调试以下网络问题：

问题描述：{如：前端调用 API 偶发 502 / 跨域错误 / 超时}

环境信息：
- 前端：{框架/部署方式}
- 后端：{框架/部署方式}
- 中间层：{Nginx / CDN / API Gateway}

请按链路排查：
1. 前端控制台和 Network 面板应看到什么
2. DNS 解析是否正常
3. SSL/TLS 握手是否有问题
4. CDN/反向代理是否缓存了错误响应
5. 后端服务是否可达（健康检查）
6. 超时配置链条（前端 → Nginx → 应用 → 数据库）
7. CORS 配置是否正确
8. 给出精准的调试命令（curl / dig / openssl）
```

## 6. 数据库死锁排查

```
请帮我分析以下数据库死锁问题：

数据库：{PostgreSQL / MySQL / SQL Server}
现象：{报错信息 / 监控发现的死锁日志}

```
{粘贴死锁日志或相关 SQL}
```

请输出：
1. 死锁的两个事务各在等什么锁
2. 事务执行顺序导致死锁的时序图（文字描述）
3. SQL 改写方案（调整加锁顺序、缩小事务范围）
4. 隔离级别是否需要调整
5. 应用层重试机制建议
6. 如何监控和预防此类死锁
```

## 7. 依赖问题排错

```
我遇到了一个依赖/环境问题：

问题：{描述：如安装依赖失败、版本冲突、运行时找不到包}

环境：
- 操作系统：{OS}
- 包管理器：{npm/pip/maven/gradle/cargo}
- 相关包的版本：
```
{粘贴 package.json / requirements.txt / pom.xml 等依赖声明}
```
错误信息：
```
{粘贴错误信息}
```

请逐步排查：
1. 错误信息解读
2. 版本兼容性检查（哪些包之间有冲突）
3. lock 文件是否正确
4. Node/Python/Java 版本是否正确
5. 缓存清理和重装步骤
6. 最终解决方案（具体命令）
```

## 8. 并发 Bug 排查

```
请帮我排查以下并发问题：

代码：
```{语言}
{粘贴并发相关代码}
```

现象：{数据偶尔不一致 / 偶发死锁 / 测试偶发失败}

排查清单：
1. 共享可变状态是否做了同步
2. 是否有 check-then-act 竞态条件
3. 锁的粒度和顺序是否正确
4. 是否有活锁/饥饿的可能
5. 异步操作是否正确 await
6. 事务隔离级别是否足够
7. 是否有丢失更新的问题

输出：问题定位 + 修复代码 + 并发测试用例（证明修复有效）。
```

## 9. 正则表达式调试

```
请帮我分析和修复这个正则表达式：

正则：`{粘贴正则}`
目标字符串示例：`{字符串}`
期望匹配结果：{描述}
实际结果：{描述差异}

请：
1. 用自然语言逐步解释这个正则的每一部分在做什么
2. 指出哪里导致了预期之外的行为
3. 写出修复后的正则
4. 提供 5 个正向和 5 个负向测试用例
5. 如果有性能隐患（灾难性回溯），指出并修复

工具参考：如果复杂，可以画一个简化的状态机描述。
```

## 10. 疑难 Bug 系统性排查

```
我有一个已经排查了超过 {X 小时/天} 的 Bug：

Bug 描述：{完整描述}

已尝试但无效的方法：
1. {方法 1}
2. {方法 2}
...

代码库信息：{语言、框架、规模}

请用系统性调试法（Systematic Debugging）帮我重新审视：
1. 我的假设是什么？哪些假设可能错了？
2. 有什么证据支持每个假设？哪些是推测？
3. 设计 3 个能区分假设的"差分诊断"实验
4. 最简复现步骤（摈除所有无关因素，最小化复现）
5. 二分法缩小范围：最近在哪次提交开始出现的？
6. 换个角度：如果这不是 bug 而是 feature，怎么解释？

不要给模糊建议——每个实验必须告诉我具体要做什么、期望看到什么。
```
