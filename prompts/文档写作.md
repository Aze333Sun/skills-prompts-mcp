# 文档写作提示词

## 1. README 生成

```
请为以下项目生成一份专业的 README.md：

项目信息：
- 名称：{项目名}
- 一句话描述：{一句话}
- 技术栈：{技术栈}
- 核心功能：{列表}
- 安装方式：{简要说明}

要求：
1. 项目 Logo（占位符）+ 徽章（License、Build、Version）
2. 一句话简介 + 3 个核心特性（带 emoji）
3. 快速开始（3 步以内跑起来）
4. 完整安装指南
5. API 速览（如有）
6. 配置说明（环境变量表格）
7. 项目结构说明
8. 贡献指南（简述）
9. 许可证

用 Markdown 输出，排版美观，阅读时间不超过 5 分钟能读完核心内容。
```

## 2. API 文档生成

```
请根据以下代码生成 API 文档：

```{语言}
{粘贴 Controller/Handler 代码}
```

对每个接口输出：
1. 接口名称与用途（一句话）
2. HTTP Method + URL
3. Headers（Auth 要求）
4. 请求参数（Query / Body / Path），每个字段的类型、是否必填、说明、示例值
5. 成功响应（HTTP 200）示例
6. 错误响应（常见 400/401/404/500）示例
7. 调用示例（curl 命令）

格式用 Markdown 表格 + JSON 代码块。
```

## 3. 技术方案文档

```
请帮我写一份技术方案文档（RFC/Design Doc）：

项目背景：{为什么做这个}
目标：{要达成什么}
非目标：{明确不做什么}

请按以下结构撰写：
1. 摘要（200 字内概述）
2. 背景与动机
3. 技术方案（至少 2 个备选方案 + 对比）
4. 推荐方案详细设计（架构图文字描述、数据流、接口定义、数据库变更）
5. 风险与缓解措施
6. 迁移计划（分阶段）
7. 测试策略
8. 上线监控指标
9. 工作量预估

语言简洁，少用套话，多用具体数据和技术细节。
```

## 4. 发布说明 (Release Notes)

```
请根据以下 Git 提交记录生成一份用户友好的 Release Notes：

Git log：
```bash
{粘贴 git log --oneline 输出，或描述本次发布的改动}
```

版本号：{vX.Y.Z}

要求：
1. 一句话总结本次发布的核心价值
2. 分类列出变更（新功能、改进、修复、废弃、Breaking Changes）
3. 每个变更一行，格式：- [标签] 描述 (#PR编号)
4. Breaking Changes 加粗 + 迁移指南
5. 致谢贡献者（如有）
6. 升级注意事项

语气亲切但专业，面向用户而非开发者。
```

## 5. 故障复盘报告

```
请帮我写一份故障复盘报告（Postmortem）：

故障信息：
- 时间：{发生时间 - 恢复时间}
- 影响范围：{多少用户 / 哪些功能}
- 现象：{用户看到了什么}

请按以下结构撰写：
1. 故障摘要（时间线一句话）
2. 影响范围（量化数据）
3. 时间线（UTC+8，关键节点精确到分钟）
4. 根因分析（5 Whys 追溯）
5. 触发的技术原因（详细）
6. 为什么没被提前发现（监控/告警/测试的盲区）
7. 恢复步骤
8. 改进措施（分 P0/P1/P2，每项有负责人和截止日期）
9. 经验教训

核心原则：对事不对人，重点在于系统如何能防止同类问题。
```

## 6. 架构文档

```
请为以下系统编写架构文档：

系统描述：{简要描述系统功能和规模}

请包含以下章节：
1. 系统概述（画文字架构图）
2. 技术栈全景
3. 核心模块说明（每个模块的职责、输入、输出、依赖）
4. 数据流（请求从进入到返回的完整链路）
5. 数据库设计（核心表 ER 关系描述）
6. 部署架构（服务器、容器、网络拓扑）
7. 关键设计决策与取舍（为什么选 A 不选 B）
8. 性能指标（P99 延迟、QPS、可用性目标）
9. 运维手册入口（监控面板、告警规则、常见故障处理）

面向受众：接手开发的新人（需要 1 天内理解系统）。
```

## 7. 代码注释规范

```
请为以下代码添加专业注释：

```{语言}
{粘贴代码}
```

注释原则：
1. 只解释 WHY（为什么这样做），不解释 WHAT（代码已经说明了做什么）
2. 复杂算法的思路说明
3. 魔法数字的含义
4. 临时的 workaround 标注 TODO + 原因
5. 非显而易见的边界条件处理

不要：函数名已经说明功能的注释、参数逐个解释的注释、改动日志式的注释。

输出注释后的完整代码。
```

## 8. 周报/月报生成

```
请根据以下工作内容生成一份结构化的周报（或月报）：

本周完成：
{列出完成的事项}

下周计划：
{列出计划}

遇到的问题：
{列出阻塞或困难}

格式要求：
1. 关键成果（量化数据，如：接口 P99 从 800ms 降至 120ms）
2. 详细进展（按项目分组）
3. 风险与阻塞（需要谁协助）
4. 下周重点

语言：简洁务实，不说"积极推进""持续优化"等套话。用具体数字代替形容词。
```

## 9. 项目提案文档

```
请帮我写一份项目提案文档（面向决策层）：

项目名称：{名称}
提出人：{姓名}
日期：{日期}

请包含：
1. 一句话价值主张（30 字内）
2. 为什么现在做（时机分析）
3. 我们要解决什么问题（用户痛点 + 数据支撑）
4. 目标用户是谁（Persona）
5. 解决方案概述（核心功能、差异化）
6. 关键成功指标（OKR，可量化）
7. 资源需求（人力、时间、预算）
8. 风险与依赖
9. 竞品对比（1-2 个最直接的竞品）
10. 下一步行动

全文不超过 2 页 A4，用数据和事实说话，避免空洞形容词。
```

## 10. 用户帮助文档

```
请为以下功能编写面向普通用户的帮助文档：

功能名称：{功能名}
适用产品：{产品名}

要求：
1. 用「你」称呼用户
2. 每一步都配文字说明（需要截图的地方标注「📷 截图：xxx」）
3. 常见错误与解决方法（FAQ 格式）
4. 阅读时间不超过 5 分钟
5. 避免技术术语，必须用的话附通俗解释
6. 文章末尾放 3 个相关功能链接

语言：像朋友在教朋友用东西，不官方、不说教。
```
